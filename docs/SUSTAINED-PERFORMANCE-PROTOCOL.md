# Sustained performance proposal, v1 (not yet an executed experiment)

## Decision and prior evidence

No Intelligent Futures performance advantage is currently established over tuned stdlib. Published 0.5 evidence rejected all 11 small homogeneous cold-lifecycle fixtures and the separate 4-graph + 4-HTTP hybrid fixture. Earlier optimizer warm passes used three held-out seeds and offer descriptive results, not a statistically supported adoption result. A plausible remaining axis is a persistent heterogeneous service whose pool startup is amortized and whose work mix shifts within its lifetime. This is a hypothesis, not a promise of a positive result.

The current adaptive policy routes explicit I/O to threads only. Process-safe CPU/unknown tasks may be diverted based on pressure, then uncontended completion observations. The runtime does not dynamically change batching. Thus any gain from a better static batch size belongs to configuration selection, not dynamic scheduling; the stdlib comparator receives the same batch grid.

Primary proposed workload: a route-planning/enrichment worker receiving bursts of graph-route jobs and HTTP object fetches. Use existing real NetworkX route validation and Requests loopback byte-digest fixtures, with generated but nontrivial graph/response inputs. Pools persist across a disjoint warmup plus a finite sustained warm job stream. The measured service is a bounded closed-loop throughput fixture, not an open-loop request-latency or real internet/network deployment.

Optional second hypothesis, not in this experiment's claim family: heterogeneous document ingestion with Python JSON/text aggregation and zlib compression, stratified by payload size. Native compression can release the GIL while Python aggregation cannot. It would require its own algorithm/reference-oracle validation and preregistration. Do not run it because the first hypothesis failed, or pool its best result with the primary without a new multiple-testing declaration.

## Workload and measurement boundaries

- Proposed fixed session: 32 disjoint warmup jobs, then 256 measured jobs, half graphs and half HTTP. Generate graph and HTTP recipes in chunks no larger than their existing representative count cap (64); do not repeat identical jobs simply to make a duration longer. Four seeded macro-epochs alternate CPU-heavy and HTTP-heavy arrivals while preserving the same total mix. Exact ratios/order algorithm must be frozen in code before any timing.
- Graph cost buckets use already available input metadata (origin/destination counts); HTTP buckets use byte length. Metadata and explicit kind hints are visible to every engine and baseline. No inferred GIL classification, undisclosed predictive features, sleeps or artificial blocking gates in the performance path.
- Standard-library process execution and intelligent task process-safety declarations are explicit opt-ins. Only generated local, repeatable, idempotent fixture work is replayed; no live user traffic, external-service requests, shared mutable application state or credentials.
- Warmup inputs are distinct from measured jobs. Pool construction + warmup are recorded separately; the primary warm timer begins only after all warmup jobs are complete and ends after every measured Future is terminal and its result retrieved. Shutdown is separately timed and included in a total-lifecycle cost. No state/profile persists across independent observations. Candidate can learn only from its own warmup and execution in that session.
- Fresh input/work paths and a fresh loopback server per observation. Sequential oracle generation is outside execution timers, but inside total discovery cost. OS/page/native caches are uncontrolled and explicitly not described as cold. Source inputs are touched by reference creation, consistently for all modes; no application response cache persists.
- Use the identical top-level tuple-batch kernel and homogeneous contiguous grouping for all engines. Batch options 1 and 4; a batch never crosses a workload/cost-key boundary. Limit accepted-but-uncollected logical jobs to 32, and validate the bound for every submit/pop. This normalizes memory/arrival pressure instead of silently comparing 32 one-item jobs with 128 batched jobs. Intelligent max_pending is 32 Future slots, with the external logical-item window as the tighter resource contract.
- Consume completion order using FIRST_COMPLETED for every engine, preserve original order only for the final digest. Avoid an ordered-results head-of-line artifact. Timestamp done callbacks, not result retrieval. Record per-logical-item arrival/submit/completion and report p50/p95/p99 overall and per family/cost stratum. Batch items share the containing batch's completion timestamp; those are batch-completion proxy latencies, not internal item service times.
- Validate every ordered result against a sequential per-seed exact digest, and preserve existing per-item invariant checks. Also validate counts, unique logical IDs, no missing/repeated results, all Future terminal states, route totals, pending counts, and clean shutdown. Server request counters verify actual fetch work, without counting sequential oracle requests as measured traffic.

## Grids and fair comparators (proposal to freeze before timing)

Total worker budgets 4 and 8. Thread-only and process-only stdlib each receive both budgets, batch 1/4. The fixed reference is 8 stdlib threads, batch 1. The tuned single-pool comparator searches those eight configurations.

Manual stdlib hybrid static routing receives splits (2 threads, 2 processes), (4,4), (2,6), (6,2), batch 1/4. CPU hints route to process, I/O hints to thread. It is a common hand-built hybrid implementation using standard executors, independent of the candidate scheduler.

Manual stdlib hybrid overflow routing receives the same splits/batches. I/O remains thread-only. CPU jobs prefer process, but divert to threads when process queued jobs exceed process capacity and the capacity-normalized outstanding difference exceeds a predeclared 1.1 threshold. This nonlearning queue-pressure policy receives the same input metadata and bounds. Track actual accepted/in-flight/completed state rather than treating the stdlib unbounded internal queue as a free buffer. It is a defined tuned hand-built comparator, not a claim of globally optimal expert code. A future calibrated service-time predictor would be another comparator, not something this benchmark has defeated.

Intelligent candidate grid: adaptive routing for those same splits/batches, predictive concurrency disabled, default exploration/deadband settings. All grids share the same total worker and logical-admission budgets. The candidate may also include deterministic single-pool modes only if listed before training; otherwise the scope is specifically the adaptive hypothesis. Select one intelligent finalist and one finalist per baseline class using training only.

## Primary inference and acceptance

- Primary endpoint: elapsed seconds to complete the fixed 256-job warm stream. Since item count is fixed, its reciprocal is fixture throughput, but inference concerns median independent paired log-speedup, not mean request throughput or future latency.
- Candidate must pass versus all four reference roles: fixed stdlib, tuned single stdlib pool, tuned static stdlib hybrid, tuned overflow stdlib hybrid. Alias-identical selected references share one measurement. Alpha 0.05 divided by four comparisons = 0.0125; no claim family across optional future workloads/campaigns. Use the exact sign/order-statistic bound and positive 1e-12 log-margin guard corresponding to evaluator v2. Test the independent calculation against the installed evaluator on synthetic paired observations.
- Required paired median speedup lower bound strictly above 5%, log-speedup MAD <=0.10, positive aggregate elapsed saving, no observed pair >25% slower, all compared warm durations >=0.001 s. Failure of any correctness/resource gate excludes adoption, not just slow successful rows.
- Additional fail-closed observational caps per entire lifecycle: 1 GiB sampled process-tree RSS, 120 CPU seconds self+waited children, 60 wall seconds. These are rejection limits, not hard memory enforcement. A supervising process can impose a declared 90-second emergency timeout and retain the timeout observation. Resource usage includes warmup, measured work, validation and waited shutdown; excludes fixture/oracle generation, reported separately as discovery overhead. Warm CPU cannot be read from waited-child counters while workers are alive; do not mislabel lifecycle CPU as warm CPU.
- Latency safety: no selected-candidate held-out overall or per-family batch p95 >1.25 times the corresponding paired reference p95, and absolute p95 <=5 s. Failure is a gate; per-key small-n tails are descriptive only. No population p95 confidence claim is made from 24 fixture-level p95 estimates.
- Report cost in three pieces: pool startup/warmup/shutdown; per-session warm work; complete development + training + reference + confirmation + analysis wall time. Compute conditional break-even in same-sized 256-job fixtures from the minimum observed paired warm saving, and also full-session saving including startup/warmup/shutdown. Do not claim a financial/developer-time benefit or actual amortization without a user-supplied reuse horizon. At most report execution advantage with adoption pending an actual horizon.

## Stop and resource coordination

No CPU-heavy measurement while the independent 4–6-hour endurance job runs. Performance must finish or pause before that exclusive window; no hidden sampling work in parallel. Lightweight syntax/source review and report analysis are safe during endurance. Development is capped; confirmation is one frozen run with every slot retained. If development shows warmup cannot stabilize or the fixture exceeds resource limits, stop and report feasibility failure rather than shrinking after viewing held-out evidence.

## Expected useful outcomes

A negative result closes the warm heterogeneous axis for this precise fixture and comparator class. A win only over fixed/single pools shows value versus a simpler integration boundary, not scheduler superiority over a well-built hybrid. A win over static but not overflow hybrids supports basic overflow routing as the cause. A full four-comparator pass is bounded evidence of warm execution benefit on this host; adoption additionally needs an actual reuse horizon and operational fit. None of these results upgrades Beta to production certification.

## Review notes before approval

Fixed warmup is not proof that all lazy workers started or adaptive profiles converged. Record per-job process/thread identities and pre-/post-measurement profile sample counts; report any worker first observed only in the measured stream. A no-barrier real-work warmup may leave a configured worker unused, which is itself part of this fixed-warmup configuration, not a reason to silently extend warmup. Call the primary scope “fixed-warmup persistent-session execution,” not a guaranteed steady state. No gated artificial warmup is included in performance numbers.

For latency, this is a saturated bounded producer. A job has no independent external arrival process. Record requested submission and callback completion; report submission-to-completion proxy latency and producer admission delay separately. Do not label it end-user response latency. If application-level ready timestamps are also reported, every measured job is available at phase start, so queueing-before-admission is included and the statistic answers a different question.

Proposed maximum observation count is 3 × (8 single + 8 static hybrid + 8 overflow hybrid + 8 intelligent) + 24 × 5 = 216, before fixed/tuned aliases collapse. Four comparison roles still permit an exact n=24 median bound; alpha=0.0125 gives the seventh ascending log-ratio order statistic as the lower bound (at least 18 strict wins above the margin). This is only a sample-size feasibility fact, not expected statistical power.

## Implementation freeze amendments (supersede corresponding proposals above)

- Runtime is the reviewed 0.5.1 candidate containing the narrowly scoped reentrant-admission guard, not the pristine 0.5 release. The canonical 15-file imported runtime manifest digest (filenames relative to the package root, sorted compact JSON) is `7774e028757fd04922b22db1cb61c5483a147fcfd11f25015536094df8f4ba4e`. The published 0.5 snapshot remains intact elsewhere. This harness makes no before/after speed claim for the guard.
- The HTTP fixture server runs in its own spawned interpreter, eliminating same-parent-GIL coupling. It shares the selected at-most-eight CPU affinity with the client/workers; the executor worker budget excludes one server process and its handler/support threads. Record peak active handlers, request counts and server lifecycle CPU, and include the complete process tree in RSS. This is local client/server evidence, not real internet performance.
- Precisely 32 precondition jobs (16 graph, 16 HTTP), then four 64-job epochs with graph/HTTP counts 48/16, 16/48, 48/16, 16/48. For each epoch, take the next generated slice from each family, sort each slice by cost key and logical ID, partition at most four same-key/family jobs per packet, shuffle packets with the declared seeded RNG, flatten. Both batch configurations consume that same stream; batches do not cross a cost key/family boundary.
- Overflow uses BATCH-slot counters, matching the scheduler's unit: `Qp=max(0, Op-P)`, spill CPU work iff `Qp>=P` and `Op/P-Ot/T>=1.1`. `O` means accepted-not-terminal Futures, `P/T` configured process/thread workers. This is a declared queue-capacity proxy, not direct OS task activity. I/O remains thread-only.
- Latencies use nearest-rank empirical p50/p95/p99, each logical job weighted once even when multiple jobs share a batch completion timestamp. Overall and per-family p95 receive the stated gates. Keys are recorded for later descriptive strata, not separately selected tail tests.
- Resource/elapsed/correctness validation is repeated from raw rows during comparison. Missing, malformed, negative, nonfinite or below-resolution values fail closed; all compared held-out rows must be eligible. A failed training configuration is ineligible for selection. Any failure of the fixed reference in training prevents confirmation.
- Fresh observation children are supervised with a 90-second complete-observation timeout and 1.5-GiB sampled emergency tree-RSS limit. This is an external emergency stop for this owned benchmark process group, separate from 60-second/1-GiB observational adoption gates. A launched-slot ledger is fsynced before work; raw partial files, per-slot supervisory state, failures and aborted slots are preserved. Bounded graceful cleanup and a second exact-identity/owned-group census verify no living owned child remains.
- Actual graph file SHA256, selected origins/destinations and HTTP byte SHA256/sizes/query metadata are bound in the fixture content digest. The campaign rejects any same-seed digest discrepancy across modes.
- All initial development time is linked with `--development-report` for the full campaign. Discovery cost reports prior development, complete campaign preparation/oracles/training/confirmation/internal-analysis wall time, and scope exclusions explicitly. Subsequent external review is not silently treated as free. Break-even is conditional arithmetic with a named numerator; any nonpositive minimum paired saving yields no finite break-even. No actual application reuse horizon has been supplied.

Exact plan and imported source identity are written before any observation. Training selections are written to a separate frozen-selection artifact before any held-out fixture executes. Development uses exactly the eight modes listed in the harness on the four development seeds; it is feasibility evidence only. No timing has been executed at this amendment's preparation.
