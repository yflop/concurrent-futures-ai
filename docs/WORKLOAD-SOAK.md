# Bounded sustained workload checks

Run from an installed checkout with optional `requests`, `requests-cache` and
`psutil` dependencies:

```sh
python -m benchmarks.real_world.soak --output benchmarks/results/soak.json
python -m benchmarks.real_world.soak --workloads pipeline sqlite http cached_http downloads discovery --seconds 60 --output benchmarks/results/soak-six.json
```

The default observes each of HTTP, SQLite and pipeline for 60 seconds of
submission, then drains accepted work and shuts down. Duration is bounded to
300 seconds **per workload**, with a hard admission count cap of 50,000 tasks
per workload. Setup, sequential reference generation, draining and teardown are
outside the admission deadline, so this is not a wall-clock termination limit.
A task cannot be killed by the harness. Hung tasks can prevent draining; a
supervising process is needed for an operational hard timeout. There are no
artificial sleeps in work and no third-party network requests.

The executor is explicitly fixed at two threads, no process workers, four
pending tasks, hints routing and predictive admission disabled. The same flags
and their provenance are recorded in the report. This configuration is a
reliability-check choice, not a calibration-selected performance winner. No
representative timing report is needed and no inferred winner is silently
substituted.

## What actually runs

Six immutable task inputs per selected workload are prepared once with
`prepare(..., scale="representative")`, seed 8701, then repeated cyclically:

- Pipeline reads JSONL, counts words, serializes and compresses each page.
- SQLite opens a fresh read-only connection/snapshot and checks aggregates.
- HTTP fetches and verifies generated bytes from a loopback fixture server.
- Cached HTTP uses a fresh invocation-specific SQLite cache, checking one cold
  miss and one warm hit on every invocation.
- Downloads fetch byte ranges, merge independent temporary outputs and verify
  size and digest.
- Discovery checks local open/closed fixture ports and device responses.

Network handlers and their listening sockets are context-managed; invocation
caches and output directories are temporary. The fixture lives until all work
has drained. Inputs are hashed before and after the observed stream to detect
mutation. These replicas also perform their own manifest/round-trip checks.
`execute_batch` obtains a sequential reference before measurement. Every
measured task calls the actual module `run_task`, and its canonical JSON digest
must match its reference. This catches executor/replay errors but cannot prove
an algorithm free of common-mode bugs shared with its sequential implementation.

## Acceptance and output

Exit code 0 requires all selected workloads and the separate exception probe
to pass. Exit code 1 reports task errors, reference mismatches, callback errors,
input mutation, incomplete duration, insufficient checks, accounting failures,
remaining new threads/processes, missing resource instrumentation or resource
budget breaches. At least 12 successful-or-failed completed checks are required
by default; any errors still fail acceptance. `--min-checks`, `--fixture-count`
(1–12), and `--task-budget` make these bounds explicit.

If the task cap is reached first, the JSON reports
`stop_reason="task_budget_exhausted"`, the actual observed duration, and
`duration_completed=false`; it never presents a short task burst as a completed
sustained observation. Extremely fast tasks may hit this cap. Reaching the
deadline with too few checks fails as well. Throughput includes drain/shutdown;
10-second time windows record completed tasks, errors and mismatches, with a
final bounded drain bucket. Results, futures, error examples and windows have
bounded retention, rather than accumulating a per-task history.

After `shutdown(wait=True)`, the executor must satisfy
`submitted = completed + failed + cancelled`, zero pending, zero rejected,
zero process submissions and peak pending at most four. All callbacks must
have run. A separate tiny deterministic fault probe checks exception propagation
to both caller and callback and the executor's failed count. Its expected error
is excluded from the measured successful workload stream. Callback failures in
the stream are explicitly caught and reported, since `Future.result()` does not
propagate callback exceptions.

## Resource measurements and limits

Process-tree RSS is sampled every 10 ms, with synchronous start/end samples.
The report includes start, peak, end and signed end-minus-start drift. The
measurement starts after fixture setup and sequential reference warm-up, ends
after executor shutdown, and includes the live fixture server. Shared pages
may be counted twice; between-sample spikes can be missed. Native allocator
retention can increase end RSS without a leak. This short check neither proves
leak-freedom nor enforces a memory limit. CLI acceptance defaults are a sampled
peak of 1024 MiB and positive end-start growth of at most 128 MiB; override with
`--max-rss-mib` and `--max-growth-mib`.

CPU uses the runner's `cpu_seconds`: POSIX SELF plus waited CHILDREN deltas for
the sampled executor lifecycle, including fixture/instrumentation threads.
The default per-workload budget is 600 CPU seconds (`--max-cpu-seconds`). Missing
CPU/RSS readings fail closed. Other processes on the host are not included;
run in an isolated process for meaningful resource and cleanup checks. After
fixture teardown, newly surviving Python threads and descendant processes are
reported and fail acceptance. Existing threads/children are excluded.

Source hashes, dependency versions, host metadata, explicit configuration,
reference digest, budgets and command line are recorded. These are local,
bounded observations, not upstream interoperability, uptime, universal
stability, statistical convergence or production deployment certification.
The unit tests use mock clocks and tiny pure functions; they do not execute
representative workloads or media tools.
