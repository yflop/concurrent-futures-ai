# Configuration-quality experiment: predeclared protocol

This experiment evaluates which backend/worker/batch configuration the package
selects, rather than timing two executors at identical settings and calling their
implementation overhead a configuration improvement. The primary experiment was
prepared on 2026-10-10. The integrated run starts only after core audit and verification.
The raw files retain each plan hash, source hashes, selection hash, and timings.

## Fixed primary design

- Eleven real local workload harnesses: HTTP, cached HTTP, downloads, discovery,
  SQLite, deduplication, data pipeline, geospatial routing, images, video and OCR.
- Actual Pillow, NetworkX, SQLite, HTTP libraries, FFmpeg, Poppler and Tesseract.
  Media algorithms are not replaced by sleeps or timing simulations.
- One actual host, restricted to eight of its nine visible affinity CPUs.
  Cgroup quota/memory-limit files are unavailable; this means unknown, not unlimited.
- 24 candidates: thread/process × workers 1/2/4/8 × batches 1/4/16.
  Every candidate has profiling interval zero. This is explicit offline selection,
  not an online prediction or self-modifying admission-policy experiment.
- Four training seeds generated by Random(1001207), then three distinct held-out
  seeds: 1010231, 1020241, 1030249. Each fixture has 24 tasks and two executor passes.
- Representative mixed-profile generated inputs, with identical seeded inputs for
  every candidate in a repeat. This is a same-generator holdout, not evidence of
  distribution shift. OS and native-library caches are uncontrolled; order is
  independently shuffled each repeat to reduce systematic order bias.
- Four selectors frozen before any held-out timing: exhaustive arithmetic mean,
  exhaustive median, primary 72-call and secondary 48-call budgeted median successive halving. The matched median
  control separates reduced-search effects from mean-versus-median differences.
- Budgeted search spends at most 72 callback evaluations versus 96 for exhaustive
  search: two repeats on all 24 candidates, then two more on 12 survivors, assuming
  no candidate fails. Failures permanently exclude candidates and may reduce calls.
- The secondary low-cost selector starts with one repeat per candidate and has a
  48-call ceiling, versus the primary two-repeat 72-call operating point. Both use
  at most four repeats. The primary is declared before measurement; held-out
  results cannot change which operating point is designated primary. Both replay
  the same measured training matrix, adding no workload trials.
- Each workload has a six-hour emergency wall watchdog, a 600-second checkpoint
  stall watchdog, and a 2 GiB observed process-tree emergency RSS limit. These
  process-level guards are separate from the per-candidate eligibility budgets.

## Objectives, eligibility and oracle

Selection minimizes combined cold executor lifecycle (construction + execution +
shutdown) plus a second warm pass in the same pool. Correctness and zero errors
are mandatory. Each repeat must also pass declared observational limits: 60-second
batch p95, 1 GiB sampled aggregate process-tree RSS, and 300 CPU seconds across the
executor lifecycle. These are generic fixture budgets, not application SLAs.

All 24 candidates are independently measured on all three held-out seeds, including
candidates eliminated by budgeted search. A candidate qualifies for the oracle only
if every held-out repeat passes every gate. A missing or duplicate row invalidates
an exhaustive-grid claim. The aggregate oracle minimizes the mean over the held-out
seeds; per-seed hindsight minima are separately labelled. Neither is a global
optimum or available to a production selector in advance.

Report cold, warm and combined regret = max(0, selected/oracle − 1), the within-10%
indicator, seed-level coverage retaining failed selections in its denominator,
and all observed failures. A result marked `accepted` means complete valid oracle
plus selected correctness/resource eligibility. It does **not** mean it met a
performance-success threshold. Near-oracle coverage is an empirical result to be
reported, including misses, not a result that can be made to pass by dropping rows.
A selector returning no eligible configuration keeps its report and full discovery
cost, contributes no near-oracle successes, and does not prevent independent
selectors or the held-out oracle from being measured. An unavailable manual proxy
keeps explicit missing comparison slots. Aggregate coverage denominators retain
all eleven planned workloads and three held-out seeds, including failed or
unobserved workloads; undefined regret values are counted and remain null.
A completed report with `accepted=false` is still completed evidence, not a
reason to stop independent workload measurements.
The three seeds and phases are correlated and are not independent deployment trials.

## Cost and reuse accounting

The comparison replays a prerecorded, actual-execution **training-only** matrix.
Virtual callback cost sums actual recorded callback durations requested by a
selector. Tiny replay bookkeeping time is separately reported and must never be
presented as a real live calibration duration. Fixture construction, serial
reference execution, held-out oracle validation, and adoption cost are separate.
The serial reference is executor-independent but uses the same workload algorithm;
fixture-specific algorithm assertions also remain in the harnesses.

Saved configuration export/load is timed and validated without rerunning calibration.
Loading checks workload, Python-runtime, hardware, scheduler and selection-strategy
identity, with fresh explicit
process consent. A match does not prove future speed or unchanged contention.
Warm execution in a reused pool is distinct from saved-configuration reuse.
A separate live-budgeted run is required to validate the real evaluator path.

## Operational bounds and follow-on scenarios

Jobs run serially under a per-workload six-hour wall watchdog, ten-minute
checkpoint-stall watchdog, and 2 GiB emergency sampled process-tree RSS stop.
These supervisory samples cannot prevent every instantaneous memory spike.
Every real trial checkpoints to disk. Unexpected exceptions persist as failed rows
or a failed run, and must not be silently omitted from the grid.

Follow-on measurements are separately labelled: actual one/two-core affinity
constraints on the same host, explicitly shifted input mixes, live budgeted
selection, and a 22-epoch approximately 20-minute lifecycle endurance mix.
None can establish cross-hardware generalization, real upstream compatibility,
unbounded reliability, or production certification. A later input or algorithm
change requires fresh evaluation rather than retuning the original holdout result.

## Integrated restart and three references

The first matrix was stopped cooperatively after nine workload checkpoints on
2026-10-10. It is superseded exploratory evidence, not the integrated release
result. Independent review found that its legacy RSS sampler did not retain
permission/enumeration failures, so a partial peak could have passed a memory
gate. No such error is proven to have occurred; the coverage was not auditable.
The corrected sampler makes any collection failure sticky and reports required
RSS as unavailable. Initial/final samples, attempts, normal child-exit races,
error counts and bounded exception-type metadata are retained.

The integrated restart also follows executor queue/lifecycle and load-aware
policy changes. Source will be frozen again after their integration review.
It adds these predeclared references, all on the same fixture splits:

1. Standard-library fixed reference: ThreadPoolExecutor with the declared
   affinity-cap worker count and batch size one. This is a resource-capped
   standard-library configuration, not an assertion about Python's uncapped
   default worker formula.
2. Manual-tuning proxy: a separate exhaustive standard-library calibration over
   the same backend/worker/batch grid, four training repeats, combined objective
   and resource/correctness gates. It is a reproducible proxy for explicit manual
   tuning, not claimed human expertise, and never selects from held-out results.
   Its full measured search cost is reported.
3. Candidate oracle: every intelligent configuration on every held-out seed,
   with all-repeat eligibility, as described above. This is retrospective and
   unavailable to either selector during calibration.

A direct sequential Python loop is additionally measured twice per held-out
fixture as a no-executor reference. Algorithms, inputs and output oracles match;
its per-item latency is direct service time rather than batched future latency.
Training engine order is shuffled within candidate/seed pairs. Held-out reference
jobs are interleaved in a seeded shuffled order with the complete intelligent grid.
Matching-config stdlib/intelligent timings are separately labelled to avoid
confusing executor overhead with configuration-selection benefit.

For 24 candidates, four training repeats per engine and three held-out seeds,
this expanded design plans 273 real trials per workload (96 intelligent train +
96 stdlib train + 72 intelligent oracle + 9 reference trials), or 3,003 trials and
144,144 measured task observations across eleven workloads, excluding references
used to validate fixtures. Raw checkpoints remain private; public report metadata
redacts machine fingerprints and local filesystem paths while preserving results.

The integrated restart uses fresh declared training/hold-out seeds above. The
superseded matrix used training source 860281 and hold-outs 910091/920101/930113;
those previous outcomes are not presented as independent validation of the new
queue/policy implementation. No candidate or objective was selected using the
new held-out measurements.
